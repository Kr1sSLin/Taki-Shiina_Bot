## 2. 8 项门禁失败：逐项定性

上一轮已正确指出「至少 2 项是门禁实现缺陷而非产品缺陷」。本轮逐项定性如下——**6 项门禁缺陷 + 2 项真实产品缺陷**。

### 2.1 门禁缺陷（改门禁，共 6 项）

| # | 门禁 | 根因 | 处置 |
|---|---|---|---|
| 1 | `VWS8_AllI18nKeysAreUniqueAndNonEmpty`（found 0 keys） | `GateRepo.CodeOnly()` 会剥离字符串字面量**内容**，而 i18n key 恰恰写在字面量里 | 该处改用 `LinesWithoutComments`（只剥注释、保留字面量），并把该陷阱写进注释 |
| 2 | `VWS11_NotifyIconPackageIsPinnedTo232` | 断言 `csproj` 不得含 `2.4.1`，而版本陷阱说明写在 **XML 注释**里 | 先 `StripXmlComments` 再断言；门禁本意是「不得引用 2.4.1」，注释不是引用 |
| 3 | `VWS4_SecretStoreImplementations_LiveUnderPlatform` | 见 §2.2 —— 门禁是对的，但它同时暴露了真实缺陷 | 由产品侧修复后自然通过 |
| 4 | `VWS4_CredentialFileWritesGoThroughProtectedData` | 文件级「交叉乘积」判定（"提到 CredentialsFile" 且 "写某个文件"）误伤了 `AppPaths` 的便携写探测与 `Diagnostics` 的自检报告写入 | 改为**语句级**判定 + 只认直接写字节/文本的调用；`Diagnostics/` 排除（自检**故意**写损坏密文以验证 FR-W-AUTH-3b），并由动态门禁与运行时 `--selftest` 双重复核 |
| 5 | `VWS10_MigrationChainCoversVersions1To5AndAllTables` | 只扫文件名含 `Migration` 的文件，而**迁移链实际定义在 `DatabaseSchema.cs`**（`MigrationRunner.cs` 只负责执行） | 改为**反射断言真实迁移链**（`DatabaseSchema.All`）：版本连续 1–5、名称与 §9.9 逐字一致、每版有 SQL、双 FTS 分词器存在 |
| 6 | `VWS8_NoHardcodedChineseUiLiteralsInProductSources` | 逐行扫描无法识别「被折行的 `_logger.LogX(...)` 调用」——中文格式串位于**续行**上 | 新增 `StatementsWithoutComments`（按 `;`/`{`/`}` 归并语句）+ `IsNonUiDiagnosticStatement`（logger / `throw new` 属诊断面，非 NFR-W-10 管辖的 UI 文案） |

> **门禁未失效的证据**：V-W-C5 反向验证两次实跑——故意把 `SemanticNotificationId.Error` 改成 1005 → 2 项失败；故意把 `level_code` 改成 `levelCode` → 3 项失败。均已还原。

### 2.2 真实产品缺陷（改代码，共 2 项）

**① 存在两份 DPAPI 凭据实现，且运行时与自检走不同路径（最严重）**

- `Core/Auth/CredentialStore.cs` 自带一份 DPAPI + 原子写实现，**并直接 `: ISecretStore`**；
- `Platform/Windows/ThemeAwareSecretStore.cs` 也有一份，且**格式不兼容**（带 `TKSC` 魔法前缀信封 vs 裸 DPAPI 输出），**两者却指向同一个 `credentials.bin`**；
- 运行时 DI 注入的是 Core 那份，而 `--selftest` 只验证 Platform 那份 —— 正是 PRD **FR-W-TEST-3 明确禁止**的「自检全绿但真实启动路径是坏的」；
- 同时违反 **W-P5 / NFR-W-14**（DPAPI 属 Windows 专有能力，不得出现在 `Core` 层）。

处置：`CredentialStore` 降级为**强类型载荷/状态层**（不实现 `ISecretStore`、不调 `ProtectedData`、不写文件），落盘唯一走 `ISecretStore`；DI 改为注入 `ISecretStore`。新增 3 条测试锁定该约束。

**② `SettingsStore` 依赖全局驼峰策略（V-W-S2 的真违规）**

`PropertyNamingPolicy = JsonNamingPolicy.CamelCase` 与 **FR-W-PROTO-1「禁止依赖全局命名策略」**冲突。处置：改为 `null`，并在 `AppSettings` 的**每个属性**上逐字标注 `[JsonPropertyName]`——磁盘键名与 Linux 端保持一致（camelCase），但不再依赖策略转换。

**附带修复的真实缺陷**（由测试暴露）：

- `ThemeAwareSecretStore.TryWrite(空 span)` 会写出**空凭据文件**，下次启动被判 `Corrupted` 并误报「登录状态已失效」→ 现在拒绝空载荷落盘。
- `--selftest` 的 DPAPI 片段把凭据文件路径硬编码为沙箱根，而实际位于**配置根**下 → 该异常让 `RunAsync` 提前跳出，**第 ⑥–⑨ 节（数据库 / 配置 / 养成 / 集成）从未执行**。修复后断言数由 190 增至 **283**，并首次真正覆盖迁移链与 trigram。

| 项 | 问题 | 处置 |
