## 3. C-3 通知语义 ID（**以 Android 为基准**）

**权威来源**：Android 端 `AppNotifier` 的渠道常量。
**本端落点**：`TKSDesktop/Platform/Notification/SemanticNotificationId.cs`
**机械校验**：`V-W-S5`（枚举值逐值断言）；`--selftest` 的 `contracts` 片段。

| 语义 | ID |
|---|---|
| `CHAT` | **1002** |
| `GREETING` | **1003** |
| `ERROR` | **1004** |
| `REMINDER` | **1005** |
| `LEVEL` | **1006** |
| `STREAK` | **1007** |
| `PROGRESS` | **1008** |

**本端特有说明**：
- ⚠️ **不得照抄 Linux 端现值**：Linux 端 1004–1006 的语义与 Android 互换（属其待修正项，见跨端 PRD §1.3.2 / 决策 6 的 `FR-A8`）。本端**直接采用 Android 基准**。
- Windows Toast **没有「渠道」概念**，但语义 ID 仍按上表分配，并通过 **相同 `ToastTag` + 覆盖组**（`SemanticNotificationIds.ToastGroup`）实现「同类通知替换而非堆叠」（FR-W-NOTI-3）。
- Java/Android 的 `NotificationChannel`（4 个，固定 ID 1002–1008）与本端 Toast 的 5 类语义映射：**Bot 错误**在 Android 侧无独立渠道，本端按上表使用 **1004**。

## 7. C-6 错误码 → 文案（14 个 + 中性兜底）

**权威来源**：后端 `api/v1/deps.py` 常量表 + `http_api.py` 字面量。
**本端落点**：`TKSDesktop/Contracts/ErrorCatalog.cs`（码 → i18n key）；文案在 `TKSDesktop/App/I18n.cs`。
**机械校验**：`V-W-S6` + `--selftest` 的 `contracts` 片段（15 个数字码逐项 + 未知码中性兜底 + 全部码均有文案）。

| code | 含义 | 本端行为 |
|---|---|---|
| `0` | 成功 | — |
| `40001` | 参数错误 | 提示并阻断本次操作 |
| `40002` | 城市为空（`PUT /settings/city`） | 提示并阻断 |
| `40101` | 鉴权失败 | 走 Token 刷新流程（FR-W-AUTH-4） |
| `40102` | Token 失效 | 走 Token 刷新流程 |
| `40201` | 积分不足 | 提示「积分不足」，用返回 `balance` **覆盖**本地缓存 |
| `40202` | 物品不存在或已下架 | 提示并刷新互动菜单 |
| `40204` | 互动 AI 最终失败（**已退款**） | 展示 `fallbackText` + 提示「积分已退回」+ 刷新余额；**不做本地补偿** |
| `40205` | 补签卡不足 | 提示并刷新 |
| `40206` | 该日期已有有效对话记录 | 提示并刷新补签日历 |
| `40207` | 目标日期非法 | 提示并刷新补签日历 |
| `40301` | 设备不在白名单 | 提示（仅运维配置 `BOT_DEVICE_TOKENS` 时可能发生） |
| `40302` | 设备数超限 | **兜底文案**（后端**死代码** —— `DeviceLimitError` 从未被抛出；真实行为是**静默顶号**，见 §9） |
| `50301` | 服务不可用 | 提示并允许重试 |
| `5000` | 服务器错误 | 提示并允许重试 |

**未知码**：`ErrorCatalog.Resolve()` 返回 `error.unknown`（中性文案，**不得显示原始数字或空白**）。

**双形状兼容（陷阱 3）**：本端错误码提取**同时兼容**「顶层 `code`」（积分路由）与「`detail.code`」（`http_api` 鉴权失败，FastAPI 二次包装）。

**两类错误约定（陷阱 4）**：`http_api` 用 HTTP 状态码表达失败；**积分体系接口用「HTTP 200 + `code != 0`」**。本端**不得只判断 HTTP 状态码**。

**WS 服务端错误码（字符串）**：`INVALID_JSON` / `UNKNOWN_TYPE` / `EMPTY_MESSAGE` / `VISION_IMAGE_COUNT_EXCEEDED` / `VISION_INVALID_MIME` / `VISION_INVALID_BASE64` / `VISION_IMAGE_TOO_LARGE` / `GEMINI_NOT_CONFIGURED` / `AI_TIMEOUT` / `INTERNAL_ERROR`。
**客户端自有错误码**：`SEND_FAILED` / `TIMEOUT` / `CONNECTION_LOST`。

## 8. C-7 WS DTO 字段名（逐字段手写）

**权威来源**：后端 `docs/互动积分等级体系_接口契约.md` + 后端源码。
**本端落点**：`TKSDesktop/Contracts/WsFrames.cs`（DTO）+ `WsFrameParser.cs`（解析）。
**机械校验**：`V-W-S2`（每个属性都有 `[JsonPropertyName]`；全仓无全局命名策略）；`--selftest` 的 `ws-frames` 片段。

**必须继承的三条帧陷阱**：

| # | 陷阱 | 本端实现 |
|---|---|---|
| 1 | `chat.message` 的 `requestId` 在**帧的顶层**（不在 `payload` 内） | `WsChatMessageFrameDto.RequestId`；`ChatService.SendAsync` 发送时置于顶层 |
| 2 | `pong` 是**顶层** `{type,timestamp}`，**无 `payload` 包装** | `WsFrameParser` 的 `pong` 分支读顶层 `timestamp` |
| 6 | WS 无效 token **先 `accept` 再发 `auth.expired`**，随后以 **4001** 关闭 | `WsFrameParser.IsAuthFailureClose(int?)` → `WsClient` 走刷新流程，**不当作可重试网络错误** |

⚠️ 本端**禁用** `JsonNamingPolicy` 全局转换；服务端字段名写错不会报错，只会静默变成默认值/空串。

**未知字段与未知帧**（NFR-W-12 / FR-W-NET-2）：解析时**先只取 `type`**，未知 type → 记 debug 日志后丢弃，**不抛错、不断连**；已知 type 内的未知字段静默忽略。

## 11. 已知漂移与不照抄项（审计要点）

| 项 | 处理 |
|---|---|
| Linux 端通知 ID 1004–1006 语义与 Android 互换 | **本端不照抄**，直接采用 Android 基准（§3） |
| `points.snapshot` 为**后端死事件**（仅有定义、无调用点） | 本端**不依赖**；重连全量对齐一律走 `GET /points/overview`（FR-W-PROG-6） |
| `/healthz` 两个进程形态不同，且 nginx 未配置其 location（可能 404） | 本端只判 **HTTP 200**，不解析响应体；404 判定为「服务可达但健康检查路径不可用」的**中间态**（EDGE-W-28） |
| `40302` 为后端死代码，真实行为是**静默顶号** | 本端能区分「被顶号」（提示「该账号已在其他设备登录」）与网络故障（EDGE-W-3） |
| `messageKind` / `greetingScenario` 等属「只增不改」 | 本端容忍缺失（W-P4 / NFR-W-12） |
| Linux 端 `allowPlaintextCredentials` 明文降级 | 本端**不移植**；凭据恒为 DPAPI 密文（FR-W-SEC-2 / V-W-S4） |
| Linux 端 87 条类型化 IPC + `IPC_ERROR_MARK` 变通 | 原生单进程下根因不存在，**不实现**（FR-W-ARCH-2） |
