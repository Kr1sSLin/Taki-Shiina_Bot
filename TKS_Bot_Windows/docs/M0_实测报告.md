## 1. 实测一：`H.NotifyIcon.Wpf` 与 `net8.0-windows` 兼容性（OQ-W-4）

### 方法

1. 用 `dotnet new wpf` 建 `net8.0-windows` 探针工程；
2. 分别对 `H.NotifyIcon.Wpf` 的候选版本执行 `dotnet add package` + `dotnet build`，观察是否产生降级警告（NU1701）；
3. 用 `nuget.org` 的 `lib/` 资产清单确认每个版本实际提供的目标框架资产。

### 实测结果（原文摘录）

**① `H.NotifyIcon.Wpf 2.4.1`（最新稳定）—— ❌ 不可直接用**

```
warn : NU1701: 已使用“.NETFramework,Version=v4.6.1, .NETFramework,Version=v4.6.2, .NETFramework,Version=v4.7,
      .NETFramework,Version=v4.7.1, .NETFramework,Version=v4.7.2, .NETFramework,Version=v4.8,
      .NETFramework,Version=v4.8.1”而不是项目目标框架“net8.0-windows7.0”还原包“H.NotifyIcon.Wpf 2.4.1”。
      此包可能与项目不完全兼容。
```

其 `lib/` 资产只有：

```
net10.0-windows7.0
net462
```

→ 在 `net8.0-windows` 下 MSBuild 会**降级使用 `net462` 资产**（.NET Framework 4.6.2 组件跑在 .NET 8 上）。

**② `H.NotifyIcon.Wpf 2.3.2` —— ✅ 采用**

```
info : 包“H.NotifyIcon.Wpf”(版本为 2.3.2)的 PackageReference 已添加...
已成功生成。
```

其 `lib/` 资产：

```
net462, net8.0-windows7.0, net9.0-windows7.0
```

→ 存在**原生的 `net8.0-windows7.0` 资产**，无任何降级警告。

**③ 完整建立（含全部 6 个依赖）的构建输出**

```
=== RESTORE/BUILD ===
已成功生成。
```

（0 警告 0 错误；构建工程同时包含 `H.NotifyIcon.Wpf 2.3.2` + `CommunityToolkit.WinUI.Notifications 7.1.2` +
`System.Security.Cryptography.ProtectedData 8.0.0` + `Microsoft.Data.Sqlite 8.0.31` +
`CommunityToolkit.Mvvm 8.4.2` + `Microsoft.Extensions.Hosting 8.0.1`）

### 结论与处置（**已落到工程**）

- ✅ **采用 `H.NotifyIcon.Wpf 2.3.2`**（提供 `net8.0-windows7.0` 资产）。
- ⚠️ **陷阱记录**：`2.4.1` 是最新稳定版却**没有** `net8.0` 资产（只有 `net10.0` 与 `net462`），
  直接使用会触发 NU1701 降级警告 —— 而本端门禁为 `TreatWarningsAsErrors=true`（V-W-C4「无编译警告即失败」），
  两者冲突会导致**构建失败**。
- ✅ 已写入 `TKSDesktop/TKSDesktop.csproj` 的注释锁定该版本，并新增机械断言 **V-W-S11**（断言版本 == `2.3.2`），
  防止后续被「顺手升级」破坏。
- ✅ `TaskbarCreated` 重注册（EDGE-W-9）：`H.NotifyIcon` 内部即处理该消息；`TrayIconManager` 另有 `ReRegister()` 兜底。
- ✅ **回退路径**（若将来该库失效）：自写 `Shell_NotifyIcon` P/Invoke 薄封装（NFR-W-8 的降级要求不变），
  仅需替换 `Platform/Windows/TrayIconManager.cs`（W-P5 平台抽象层的设计目的）。

## 2. 实测二：DPAPI（`ProtectedData`）往返与失败行为（OQ-W-1，P0）

### 方法

`net8.0-windows` 控制台探针，引用 `System.Security.Cryptography.ProtectedData 8.0.0`，执行：
① 加密往返；② 密文可读性检查；③ 损坏密文解密；④ `File.Replace` 原子写。

### 实测输出（原文）

```
=== M0-2: DPAPI (ProtectedData) round-trip ===
PASS  ProtectedData.Protect(CurrentUser) succeeds :: 294 bytes
PASS  ciphertext does not contain plaintext token
PASS  Unprotect returns original bytes
PASS  Unprotect(corrupt) throws CryptographicException
```

### 结论

| 断言 | 结论 | 对应条款 |
|---|---|---|
| `ProtectedData.Protect(..., DataProtectionScope.CurrentUser)` 可用 | ✅ | FR-W-AUTH-3 / OQ-W-1 |
| 密文**不含**明文 token | ✅ | **V-W-S4 / FR-W-SEC-2** |
| `Unprotect` 往返一致 | ✅ | FR-W-AUTH-3 |
| 损坏密文抛 `CryptographicException`（**不是**静默返回垃圾） | ✅ | FR-W-AUTH-3b / EDGE-W-11 |

**由此确立的实现约束（已落到代码）**：

- `credentials.bin` 内容恒为 DPAPI 密文；**无任何明文写入路径**；**不实现**明文降级分支
  （不移植 Linux 端的 `allowPlaintextCredentials`）。
- `TryRead` 以 `SecretReadStatus` 三态返回：`NotFound`（首次启动）/ `Success` / **`Corrupted`**
  （换 Windows 账户、文件损坏）—— `Corrupted` 时**不静默清除文件**（FR-W-AUTH-3b）。
- `TryWrite` 失败（域策略 / 用户配置文件损坏）→ **不持久化、仅内存持有 Token、明确告知用户**
  （EDGE-W-11 分支 ①），**不得**降级为明文。
- 跨账户解密失败的行为 = `Corrupted`（V-W-B23 的自动化等价断言已在 `--selftest` 的 `dpapi` 片段实现）。

### 附带实证：原子写（FR-W-SEC-2a）

```
=== M0-5: atomic credential write (temp + File.Replace) ===
PASS  File.Replace atomically swaps credential file
```

→ 临时文件 + `File.Replace(tmp, target, null, ignoreMetadataErrors: true)` 可用；自检另断言「不留临时文件」。

## 3. 实测三：SQLite / FTS5 `trigram` 可用性（FR-W-DB-2 / §9.5）

### 方法

`Microsoft.Data.Sqlite 8.0.31` 的内存库 + 文件库探针，执行：
① 版本检查；② 建 `unicode61` 与 `trigram` 两张 FTS5 虚拟表；③ 中文整串 vs 子串匹配对比；④ LIKE 回退；⑤ PRAGMA 与 `integrity_check`；⑥ 陷阱 8 复现。

### 实测输出（原文）

```
=== M0-3: Microsoft.Data.Sqlite / SQLite version + FTS5 trigram ===
PASS  sqlite_version >= 3.34 (trigram) :: 3.53.3
PASS  fts5 trigram tokenizer available
    unicode61 full-string match  = 1 (expect 1)
    unicode61 substring match    = 0 (expect 0 -> confirms PRD FR-W-DB-2)
    trigram  substring match     = 1 (expect 1)
    trigram  match(熊猫)         = 0 (expect 0, no such text)
    LIKE 2-char fallback         = 1 (expect 1)
    LIKE no-hit returns empty    = 0 (expect 0)
PASS  unicode61 CANNOT match CJK substring (PRD basis holds)
PASS  trigram CAN match CJK substring
PASS  LIKE fallback works for short query
```

### 结论

| 断言 | 结论 | 对应条款 |
|---|---|---|
| 内置 SQLite 版本 **3.53.3** ≥ 3.34（trigram 前提） | ✅ | FR-W-DB-2（**M0 硬性要求：实测断言**） |
| `tokenize='trigram'` 可建表 | ✅ | §9.5 |
| `unicode61` **不能**中文子串命中（`递归函数` 在 `今天写了一个很长的递归函数` 中 MATCH 结果为 0） | ✅ **实证 PRD 论断成立** | FR-W-DB-2 |
| `trigram` **能**中文子串命中（结果为 1） | ✅ | FR-W-DB-2 |
| 1–2 字符查询走 `LIKE` 可命中 | ✅ | FR-W-CHAT-17 |
| `LIKE` 无命中返回空集而非报错 | ✅ | FR-W-CHAT-17 |

→ **双索引方案（`chat_messages_fts` unicode61 + `chat_messages_fts_tri` trigram）+「≥3 字符走 FTS、1–2 字符回退 LIKE」的策略得到实证支持，按 OQ-W-7「先按 §9.5 双索引实现」落地。**

### 附带实证：PRAGMA 与完整性检查（FR-W-DB-7 / DB-8）

```
=== M0-4: pragma / WAL / foreign_keys / busy_timeout on file db ===
PASS  journal_mode = wal :: wal
PASS  foreign_keys = 1 :: 1
PASS  busy_timeout = 5000 :: 5000
PASS  PRAGMA integrity_check returns 'ok' on healthy db
```

### 附带实证：陷阱 8 —— `INSERT OR REPLACE` 确实清空附件子行

```
    child rows after INSERT OR REPLACE = 0 (expect 0 -> trap confirmed)
    child rows re-inserted then UPDATE = 1 (expect 1)
PASS  INSERT OR REPLACE wipes attachment child rows (trap #8 real)
PASS  UPDATE preserves attachment child rows
```

→ 在 `ON DELETE CASCADE` 外键下，`INSERT OR REPLACE` **真的**会连带删掉子行（此处为附件行）。
**结论：数据层更新 `chat_messages` 必须用 `UPDATE`；`upsert` 语义按「先 SELECT → 无变化则不写 → 否则 UPDATE → 不存在则 INSERT」实现**（FR-W-DB-1），
且**不移植**另一端的 `repairOrphanedAttachments()` 孤儿修复逻辑（本端从第一行代码起规避）。

## 4. 实测四：资源清单与占位图机制（FR-W-UI-12 / V-W-S12，OQ-W-8）

### 方法

1. 建立 `TKSDesktop/Resources/Assets/asset-manifest.json` —— **单一资源清单**，记录
   `logicalName` → `fileName` → `expectedSizes` → `status`（`placeholder` / `final`）。
2. 程序化生成占位应用图标（**熊猫意象 + 第 4 档「黑白骑士」配色 `#3E6FA8` → `#1B3B63`**），
   输出多尺寸 ICO（**16/24/32/48/64/128/256**，PNG 压缩条目）。

### 实测输出（原文）

```
generated ...\TKS_Bot_Windows\TKSDesktop\Resources\Assets\tks-desktop.ico (20.4 KB, 7 sizes)
=== verify ===
size=20895 reserved=0:0 type=1:0 count=7
```

→ ICO 头校验：`reserved=0`、`type=1`（图标）、`count=7`（7 个尺寸条目），文件 20.4 KB。

### 结论

| 要求 | 结论 |
|---|---|
| 清单存在且集中管理逻辑名 → 文件名 | ✅ `Resources/Assets/asset-manifest.json`（18 项） |
| 代码只引用逻辑名（`AssetProvider` 解析），不得写死文件名 | ✅ 已确立约定（V-W-S12 机械断言） |
| 占位项**如实计数**，不得标记为 `final` | ✅ 清单汇总：`total=18, final=0, placeholder=18` |
| 「正式资源到位后一步替换」 | ✅ 仅覆盖同名文件 + 把 `status` 改为 `final`，**无需改代码或 XAML** |
| 应用图标含 16/24/32/48/64/128/256 多尺寸 | ✅ 实测 7 尺寸 |

**说明（OQ-W-8「等后续」的落地口径）**：
- FR-W-UI-8 优先级已由 P0 降为 **P1**（PRD §6.10）；正式 `.ico`、7 档徽章、5 个物品图标、头像**均未交付**，属**后置交付物**，**不阻塞 v1**。
- 服务端 `iconUrl` 当前**恒为空串** → 界面按「`iconUrl` → `icon`(emoji) → 内置占位图」三级回退（FR-W-INT-9 / EDGE-W-23），**不渲染破图**。
