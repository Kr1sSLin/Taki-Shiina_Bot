### 连续陪伴天数推算的口径说明（PRD 5.1a 字面实现）

`continuous_days` = 从 `daily_activity_log` 中**最大日期**向过去逐日回溯、遇到第一个缺失自然日为止的长度；
`gap_days`（最大日期距今天数）≥ 5 时按断签处理（`continuous_days=0`、等级回落 `NONE`）。
因此：

- 缺 1 天不会立刻“清零”，但用户下次对话后连续天数会重算为 1（等级回落），此时用补签卡补上缺口即可跳回原等级 —— 与 US-14 描述一致；
- 断签前 3～4 天会收到提醒（FR-18），提醒期间等级仍按最后一条记录展示。

## 4. 非功能性需求

| 项 | 落地 |
|---|---|
| 一致性 | 后端唯一数据源；客户端 Room(`user_progress`) 仅缓存，收到 WS 事件/查询结果即覆盖 |
| 性能 | “3 秒”定义为首次尝试的响应预期；客户端 `chat.typing` 展示思考态；15 秒总兜底后判定失败退款 |
| 并发安全 | 单进程内线程锁 + 跨进程 `flock`，事务内完成读改写 |
| 时区一致 | 统一 `time_utils` 业务时区（默认 UTC+8） |
| 安全 | 复用 JWT + 设备白名单（`api/v1/deps.py`），全部接口需鉴权 |
| 数据安全 | 积分/等级/流水/补签卡全部 AES-GCM 落盘（`secure_storage`） |
| 可观测性 | AI 最终失败、退款失败、定时任务异常接入 `alert_sender`；重试次数与累计失败数写入日志与告警 |
| 可配置性 | 物品/模板/等级阈值/积分规则/重试策略均可后台改，热加载、无需发版 |

## 6. 已知取舍与注意事项

1. **新增 REST 路由挂在 `ws_api.py`**：积分数据必须与 WebSocket 连接、对话历史同进程，否则无法做到“改完即推”且会出现多进程双写账本。反向代理需把 `/api/v1/interaction|points|level|admin` 指向 WS 服务端口（README 已给出 nginx 片段）。
2. **`http_api.py` 的 `POST /api/v1/chat` 不参与积分结算**：App 的对话全部走 WebSocket（`ChatViewModel` 只把 REST 用于历史/记忆/城市）。如需 REST 对话也计分，应把该接口迁到 `ws_api` 进程。
3. **15 秒兜底与“最多重试 5 次”**：单次尝试超时 5 秒，因此 15 秒内通常只能完成 3 次尝试；这是需求方选定 15 秒总上限后的必然结果（PRD 九节所述冲突的取舍）。
4. **`tests/test_text_utils.py` 为改动前就存在的失败用例**（引用了早前重构中已删除的 `split_into_bubbles`），本次未修改，运行其他用例请加 `--ignore=tests/test_text_utils.py`。
5. **`points_ledger` 等数据文件已加入 `.gitignore`**，首次启动自动创建；配置文件 `config/gamification_config.json` 亦为自动生成，可直接编辑或走 admin 接口。
6. **心情刷新成本**：每小时 1 次 DeepSeek 调用/用户（`max_tokens=200`），整晚无人也照刷；若想省，可在 `scene_refresh_scheduler` 里加"最近 N 小时无活动则跳过"。
