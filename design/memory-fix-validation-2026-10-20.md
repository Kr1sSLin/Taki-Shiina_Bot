## 三类修复进入实际提取链路

### 候选身份由模型选择，版本由服务端绑定

`TextGenerator.extract_with_context` 在调用前复制允许处理的候选快照。模型可选择 `fact_id`，返回给仓储的 `expected_revision` 则取自该快照，不再由模型生成未来版本号。未知候选 ID 明确拒绝；仅有用户提供的 `target_text` 时，保留原受控唯一身份匹配路径。

绑定的是**调用前版本**，不是返回时最新版本。新增并发测试确认：模型调用期间事实已改动，旧快照仍被仓储 CAS 拒绝，不能覆盖新事实。禁用、权限及 owner 检查继续执行。

### “今天/明天”得到可引用日窗，不推断现实结果

服务端按源消息接收时间和北京时间生成 `day_windows`。模型将明确的日期表达映射到窗口；对于原文可核验、主体为用户且明确自述的临时状态或计划，生产提取器可补齐唯一明确日期的缺失截止窗。

已有明确时间范围、持续状态 `ongoing`、不匹配日期、多日期歧义、无时间锚点或非明确用户证据不会被改成单日日窗；同事实证据关联保留旧时间范围，正常变化的新事实独立处理时间范围。窗口结束只停止把它当作当前状态引用，不表示已经康复或旅行已经完成。

### 提取改用非思考 JSON 输出，澄清语义优先级

仅记忆提取请求增加 `thinking.type=disabled` 和 JSON 对象模式；普通回复、礼物生成和检查器的思考配置未改。接口默认开启思考，关闭参数依据 [DeepSeek Chat Completions 文档](https://api-docs.deepseek.com/api/create-chat-completion/)。

模型返回 `{"facts": [...]}`，已有调用入口仍返回列表，并继续兼容旧数组响应。提取规则明确区分：

- 对唯一旧事实的模糊矛盾先输出 `dispute`，而不是因为没有明确新事实就漏掉争议。
- 正常变化使用 `change`，结束旧事实当前适用范围，另建新事实。
- 中性的新购买等已完成经历仍作为 `past_event` 提取，不因已有偏好候选而漏掉，也不误设为争议。
- 事实文本使用规范主体和偏好格式，原话、程度与变化信息保留在证据及操作/时间字段中。

评测对象仍是实际供仓储使用的生产提取器输出。版本绑定和日期处理属于已部署代码，不是评测脚本为答案补字段；JSON 证据同时保留原始模型对象，便于分辨两层结果。
