# 阶段 D：角色日常与人设

依据 PRD-04 v0.3，承接现有阶段 A/B/C 的加密存储、授权记忆与受控聊天。用户已确认：先按文档中的“短句接话、具体关注、熟悉调侃、适度暧昧”实现，最终风格人工验收。

本次实现范围为本地后端与离线验证；人工文字评审、真实模型语义质量与部署尚不记为通过。未修改正式运行配置或读取生产正文。

最终确认：用户选择先审阅固定样例，暂不调用真实模型；本次不开展真实模型回放。

## P01 公共人设与约束

`services/public_policy.py` 集中固定人设、关系、公约正文、版本及哈希。聊天、重写、检查、提取、摘要、后台候选与图片任务都装配同一契约。文本模型唯一底层调用在 `checked_completion`，外发前校验首条 system 的完整契约；缺失、改字或版本缺失会在调用前失败。图片模型入口同样校验公共正文。

新回复审核回执同时绑定公约、人设及关系版本。正式装配会阻止旧人设下已审核、尚未发送的回复直接交付。

`PromptService` 移除了固定毒舌、占有欲、固定比例词库与随机“正在做”。旧场景缓存不能变成事实；原场景刷新接口保留兼容返回空内容，不调用模型或制造兜底活动。未映射旧画像与 USER_MEMO 仍不能旁路进入上下文。权限恢复门禁仍检查。

## P02 日常事件与时间

`DailyEventMixin` 复用 `ReliableChatStore`，不另建数据库。内容在 `character_daily` 域加密，证据类型为 `authored_daily`，主体为 character；没有用户事实的 0.3→0.6 晋级或使用强化。

事件保存 eventId、修订、类型、对象、参与者、planned/in_progress/completed/cancelled 状态、计划/发生时刻、UTC 与东京本地时刻、角色日期、前序修订、真实来源引用、规则版本及审查回执。购物另保留 not_bought/bought 结果；计划不得携带已经发生的时刻，购买结果要求完成记录。取消不能自动恢复为进行，已完成不能退回计划。

同一对象后续沿用 eventId。完整修订历史沿用 `memory_revisions`；新修订强制更新内容修订标识，即使摘要相同也能使旧交付依据失效。普通记忆写接口不能创建或改写日常事实，只能显式禁用/恢复既有事件。旧的未审查日常不会自动获得引用资格。

`daily_commits` 保存东京自然日的机会幂等记录；日键、机会键均为加密索引。`daily_references` 单独记录已被聊天使用的事件版本，阶段为回复提交；未发送回复被撤销时同步标记撤销，不能继续作为模糊接续的锚点。引用记录不进入用户证据账本。

## P03 候选、检查与后台运行

后台流程：选择东京时段及当前获准事件 → 产生候选或 null → 服务端结构/时间/身份/状态检查 → 独立语义检查 → 短事务复核并提交。未完事件优先；作息不证明活动已发生。

语义检查须逐项批准普通范围、固定关系、官方冲突、连续性、时间、用户证据，classification 必须为 ordinary；不确定、缺项、JSON 无效、服务故障或 null 都不会新增事件。高确定性重大新事实另有狭窄硬规则拦截，配合完整语义检查，不把词表当完整识别。否定、假设、讨论官方旧事与新创事实分开判断。

检查回执绑定候选与上下文摘要。正式提交在用户协调锁及短事务内重新检查 event heads、权限代次、官方版本、东京日期、任务租约与日配额。候选被改、并发续写、权限变化、跨日或磁盘故障不会留下半条事实、半个修订或错误成功状态。日常与 durable job 成功状态原子提交，崩溃后不能重复制造事件。

`daily_snapshot(owner, source_ids=...)` 只允许引用属于该用户的真实源请求和逐字片段；ID 存在不等于语义支持，仍须检查主体、承诺及时间。自动后台生成默认不读取旧聊天正文，不虚构共同经历。无真实来源的用户参与一律拒绝；原始图片不被当成用户自述证据。

后台使用独立 durable worker，聊天 worker 不领取日常任务；每次模型调用最多 25 秒，单机会不重试凑数。当天无内容或失败可以空缺，过期机会不补造昨天。持久任务幂等可防止 HTTP、WS 多进程重复调度同一机会。

## P04 聊天引用

聊天从获准事件最新修订按相关性读取，模型同时看到状态、对象、结果、时间、前序和来源，不能只凭摘要猜完成。问“在干嘛”可以读取当天或未完事件，但旧进行状态只表示记录时在做，不能证明此刻仍在做。无记录时普通接话，不启动活动生成。

“下午那段呢”“后来呢”可定位最近被引用且未撤销的事件，再读取其最新修订。跨日仍是同一 eventId，不随机重建。最终完整回复和重写仍通过阶段 C 的证据/主体/否定/时间/关系/重大事件/风格检查；事件变化会阻止旧草稿提交或首次交付。

可以从 `daily_snapshot` 的合格事件中选主动消息素材，但本阶段不主动发送；窗口、配额和用户通知时区继续由 PRD-05 负责。积分/等级业务保持既有结算，关系不据积分变化。

## 配置与运维

| 配置 | 默认 | 含义 |
|---|---:|---|
| CHARACTER_DAILY_ENABLED | 0 | 关闭新的原创候选；人工验收后在部署配置中设 1。关闭不删除或降级既有合格记录。 |
| CHARACTER_DAILY_MAX_PER_DAY | 2 | 东京自然日最多提交的小事/续写数；调试范围 0～8，允许实际为零。 |

试点在东京 07:00～23:00 为已存在的聊天用户分配均匀的后台生成机会，默认两次机会对应 07:00～15:00、15:00～23:00。调度每 30 秒检查一次，同一机会最多尝试一次；这不是强制内容配额、固定学校/打工时间或发送窗口。更改调试参数不会绕过当前数据库中的已用日上限。

服务启动现有可靠 runtime 时装配；HTTP/WS/统一入口共用存储，多进程依靠持久幂等与租约。升级保留现有密钥，沿用阶段 A 的备份/恢复流程。恢复权限未核验时不得运行后台生成。新增表通过幂等建表加入现有库，备份包含这些表。
